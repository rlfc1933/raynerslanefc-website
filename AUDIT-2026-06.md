# Rayners Lane FC — Full Site Audit (Front + Staff Admin)

_Audit date: 30 June 2026. Read-only review of front-of-house pages, the staff admin portal (`admin.html`), shared JS, and the Netlify functions backend. Nothing was changed — this document plus `CLAUDE-CODE-FIX-PROMPT.md` are the only outputs._

## How the system actually works (so the findings make sense)

The site is static HTML on Netlify. The staff portal (`admin.html`) is the **writer**: it calls `pushToGitHub(name, data)` → `POST /.netlify/functions/save-data` with `{pin, path:"data/<name>.json", content: base64(JSON)}`. That function commits the file to GitHub, Netlify rebuilds, and the public pages **read** `data/*.json` and render it. So "I changed it in admin but the site didn't update" almost always means one of three things: (a) the page that should show it is hardcoded and never reads the JSON, (b) the save was built from a stale copy and got overwritten, or (c) the page reads the JSON but a different field/priority rule hides it. All three exist here.

The field-level data contract is mostly sound — Claude Code matched the writer and reader keys well across ~20 data domains. The real problems are structural: a data-integrity bug in saves, a few pages that bypass the data files, and some logic/priority traps.

## CRITICAL & HIGH — fix these first

### 1. Stale-copy saves silently revert other staff's changes (data-loss bug class)
Every editor **except News** saves the *entire* JSON file from an in-memory array that is loaded **once** at login (`loadAll()`, `admin.html:2970`). Staff mutate that array and push the whole object back without re-reading the live file first. Examples: `saveSquad` (3395), `saveCommittee` (3498), `saveSponsors` (4554), `savePatrons` (5265), `saveAttendance` (5313), `saveMeetings` (4424), and ~20 more.

Consequence: if staffer A opens the portal, staffer B publishes something, then A saves later, **A's save overwrites B's work** with A's stale base. This already bit the club once — the News editor was specifically patched against it (`commitArticle`/`deleteArticle` now re-fetch live data first; see the warning comment at `admin.html:3414`). That fix was applied to news only; every other editor still has the original wiping pattern.

**Fix:** every save must re-fetch its own JSON from the live site immediately before mutate-and-push, mirroring `commitArticle`. (This is the single most important fix.)

### 2. `investment.html` sponsors are hardcoded — admin sponsor edits never appear there
`investment.html` lines ~295–311 list Hanlon Dry Lining / McCafferty's Bar / Higginson Stairs as static HTML and **do not fetch `sponsors.json`**. The homepage strip reads the data file, but this page doesn't. Editing sponsors in admin updates the home page and not this one — a very likely source of "I updated the sponsor and it's still wrong." **Fix:** render this block from `sponsors.json` like the homepage does.

### 3. `news.html` has four baked-in articles that admin can't touch
`news.html` `BAKED_ARTICLES` (lines ~353–374) hardcodes the launch story, league allocation, trials, and sponsorship guide. They always render on top of admin-written news and **can't be edited or removed from the portal** (admin news is merely added alongside, deduped by title). **Fix:** migrate these four into `data/news.json` as normal articles (preserving their external links / dates) and delete the baked array, so the newsroom is fully admin-managed.

### 4. Match Day "next opponent" is overridden by fixtures on the homepage
When `matchday.json.isLive` is false, the homepage **ignores** matchday's opponent/date and uses `fixtures.json` for the next match/countdown (`js/main.js`). So a staffer who sets the next opponent in the Match Day editor sees no change on the home page if any upcoming fixture exists. It's a priority rule, not a crash — but it reads as a bug to staff. **Fix:** either make the Match Day editor write the next fixture too, or clearly label in admin that the countdown comes from Fixtures unless a match is Live.

### 5. Squad grid and player profiles are two separate files that must be edited together
The squad **grid** on `squad.html` reads `squad.json` (`{players:[{no,name,pos,apps,goals}]}`); the **profile pop-up** reads `players.json` (richer record incl. `photo`, `bio`). The squad editor doesn't write a `photo`, and the two files are edited independently, so it's easy to get a grid card with no profile, or a profile no card links to. Both files are currently empty. **Fix:** unify into one squad editor that writes both shapes (or one file), and include the photo field in the grid record.

## MEDIUM

6. **Safeguarding names on `policies.html` are baked in** ("Jenny Pitt", "Pete Singh", "Emma Galloway") and `officials.json` only text-swaps them **if the new name differs from the exact baseline string**. A mismatch silently leaves the old name on a safeguarding policy page. Make policies render the names from `officials.json` directly rather than string-replacing.

7. **Front-of-house chrome glitches** (all in `js/components.js`, which injects the global nav/footer): footer "Match Day → Results" links to `fixtures.html#results` but no `#results` element exists (add the id or repoint to `#calendar`); the footer has **two links both labelled "Sponsorship"** — the second (→ `contact.html`) is almost certainly meant to be "Volunteer" (→ `volunteer.html`, which is missing from the footer); and `media.html` is orphaned — it's in `sitemap.xml` but not linked from nav or footer anywhere.

8. **Two divergent brand-token systems.** `brand/tokens.css` (`--rl-*`) declares itself the single source of truth but is only used by `admin.html` and `programme-print.html`; every other page is styled by `css/style.css` with a *different* token set (`--yellow`, `--green`, `--font-c`…). They duplicate the same hex values under different names and can drift. Pick one system.

9. **Security posture (small-club appropriate, but worth knowing):**
   - The match-finances "analytics" gate is **client-side only**, its password hash is written to `data/config.json` which is **public**, and `data/analytics.json` itself is a public committed file. Match takings/attendance are effectively public to anyone who opens the data file. If that data is sensitive, it must move behind a server function, not a JS gate.
   - `data/emails.json` is committed to the public repo; any real personal emails entered become world-readable.
   - The role model ("Chairman-only" tiles) is **cosmetic** — the shared PIN is the only real gate; any logged-in user can open restricted panels from the console. Fine for a volunteer tool, but don't treat roles as security.

10. **Default PIN and staff password are shipped in source and printed on-screen** (`admin.html:2384` PIN `19332026`; `:2550` staff default `20raynerslanefc26`; both printed in the in-app guide at `:1979`). The client PIN can't really be secret (it's in page source), but it should at least be rotated and removed from the printed guide, and `ADMIN_PIN` should be set in Netlify so the repo default isn't the live gate.

11. **Unreachable fields:** committee `featured` flag and committee `photo` are never set by the add form (`admin.html:3483`); patron `photo` is hardcoded `''` (`:5251`). Public pages render these fields, so they're dead capabilities until the forms collect them.

## LOW / polish

12. Heavy hardcoded-hex usage in inline styles despite the brand rule (e.g. `programme-print.html` ~91 literals, `fan-zone.html` ~51, `index.html` ~43) — should reference tokens.
13. `programmes.html` missing from `sitemap.xml`; `media.html` present in sitemap but unreachable; missing meta descriptions on `news-article.html` and `player.html`.
14. Dead nav code in `components.js` (queries `#nav-burger`/`#hamburger`/`#mob-menu` that the current markup no longer generates — harmless, null-guarded, but should be removed).
15. `uploadImg` (`admin.html:5389`) silently falls back to inlining base64 data URLs into the JSON on upload failure, bloating files instead of surfacing an error.

## What's working well (so you don't "fix" it)
- The save proxy keeps the GitHub token server-side and allow-lists write paths to `data/*.json` and `img/uploads/*` — solid.
- `pushToGitHub` surfaces success/error to the user; saves don't fail silently.
- Staff custom passwords are properly salted-SHA-256 in Netlify Blobs (it's just that nothing enforces them for writes).
- The delete-persistence bug class was already found and fixed for news.
- Every internal page link resolves; no missing local image/CSS/JS assets; defensive `try/catch` around all front-end fetches; the service worker correctly never caches data files.

## Where your Claude / Cowork plugins fit the staff portal

The portal is run by club volunteers, so the highest-value use of the installed plugins is **content generation in Cowork that staff paste into the existing editors**, plus a few build improvements:

- **`marketing:draft-content` / `content-creation`** — drafting news articles and match reports from a few bullet points (the News and Match Report editors are blank-page today). Pair with **`marketing:email-sequence`** for member/sponsor newsletters.
- **`small-business:run-campaign` / `canva-creator` / `content-strategy`** — turn a match result or fixture into platform-specific social captions and Canva graphics; this maps directly onto the manual Post Studio / Social tab.
- **`sales:account-research` / `draft-outreach`** — sponsor prospecting and personalised outreach driven by the existing `sponsor-crm.json` data and the placeholder pitch templates (`generatePitch`, `admin.html:4284`).
- **`design:design-system`** — the right tool to reconcile the two token systems (finding #8) into one.
- **`design:accessibility-review`** — a proper WCAG pass on the public pages before the season.
- **`engineering:code-review`** — ongoing review of Claude Code's fixes, especially the data-integrity change in finding #1.

A natural next step is a small "Draft a post" helper inside admin that calls a content skill, but the fastest win is just using these skills in Cowork now and pasting the output in.
